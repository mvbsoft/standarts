# Стандарт на одній сторінці

> Версія 1.0.0-draft · Українська · [English](GUIDE.md)

Карта: який вигляд має проєкт, що робити в кожній ситуації, яка команда це робить і де деталі.
Кожне правило має ідентифікатор, наприклад `ENV-09`; правила — у [`standard/`](standard/README.uk.md),
причини — у [`decisions/`](decisions/), точні кроки й повідомлення — у `docs/how-to/` самого проєкту
(файли в [`templates/project`](templates/project/docs/how-to/operations.md)). Рівні: **M** ядро
або «наполегливо радимо», **R** радимо, **O** пропонуємо ([як їх читати](standard/README.uk.md#як-читати)).

## 1. Ідея

- **Усе працює в Docker.** На хості лише інструменти, які називає
  [PRN-01](standard/01-principles.uk.md); кожен мовний інструмент працює в dev-контейнері проєкту.
- **Один спосіб роботи.** Кожен проєкт, якою б мовою він не був, налаштовують, перевіряють,
  відправляють, розгортають і відкочують тими самими командами `make` (PRN-10, DOC-04).
- **Один файл — одне середовище.** `docker-compose.dev.yml`, `.stage.yml`, `.prod.yml`; файла за
  замовчуванням немає, тож голий `docker compose up` нічого не запускає (PRN-02).
- **Stage і prod запускають той самий вміст.** Кожен сервер сам збирає свої образи з коміту, який
  розгортає; stage і prod різняться лише своїм `.env` (PRN-03).
- **Fail closed.** Секрет без значення зупиняє старт; перевірка, яка не запустилася, ніколи не
  зелена (PRN-04).
- **Зроблено = тести, документація і реєстр** (файл `docs/reference/project-registry.md` у проєкті, DOC-03). Нічого не додають «про запас» (PRN-05, PRN-06).
- **Самодостатність і записані винятки.** Клону, Docker і `make bootstrap` досить на будь-якій
  машині; кожен виняток має причину в реєстрі проєкту (PRN-07, PRN-09).

## 2. Середовища

| | dev | stage | prod |
|---|---|---|---|
| Де | ваша машина | stage-сервер | prod-сервер |
| Код | змонтований з вашої теки; правка діє одразу | запечений в образ, який зібрав сервер | так само |
| Запуск | `make dev` | `make stage` | `make prod` |
| Гілка | ваша | `STAGE_BRANCH` (`main`) | `PROD_BRANCH` (`prod`) |
| Інструменти | один `dev`-контейнер з усіма інструментами, плюс база й інші сервіси | жодних: лише продукт | так само |

Кожне середовище — це клон репозиторію зі своїм `.env`; рядок `PROJECT_ENV` каже, яке це
середовище, і команда чужого середовища тут відмовляється працювати (ENV-04).

- **Stage і prod: по одній копії на машину.** Другий клон перебрав би контейнери, томи й дані
  першого, тому його відхиляють, без жодного обходу.
- **Dev: копій може бути кілька.** Git worktree сам отримує свої контейнери, базу й порти. Інший
  клон проєкту першого разу потребує `make dev NAME=2`; без цього його відхиляють, поки існують
  контейнери першого.

## 3. Що робити в кожній ситуації

### Про що вас питають

`new`, `adopt` і повторне налаштування проєкту питають про кожен вибір TYP-01, по одному
питанню, вашою мовою: що ця частина дає, приклад, ризик без неї і порада агента. Про те, на що вже
відповідають файли проєкту, не питають. Ваші відповіді йдуть у розділ 0 реєстру, а частину, від
якої ви відмовилися, не вважають відступом. Ядро, 24 вибори та їхні типові значення:
[TYP-01](standard/07-project-types.uk.md#the-choices); питання:
[`prompt/questions.md`](prompt/questions.md); чому так: [D-0028](decisions/0028-interactive-setup.uk.md).

### Новий проєкт

Вставте промпт із [README](README.uk.md) в агента в порожній теці (режим `new`). Агент питає те, що
можете вирішити лише ви, створює каркас із [`templates/`](templates/README.md), доводить у пробній копії,
що все працює, і комітить після вашого схвалення. Далі ваше: віддалений репозиторій і перший push,
сервери ([Перший сервер](#перший-сервер)) і, якщо ви їх обрали, копія бекапу поза сервером, монітор її heartbeat і монітор сервісу status.

### Наявний проєкт

Той самий промпт у теці проєкту (режим `adopt`): аудит за кожним правилом, звіт поза репозиторієм,
ваші рішення, план у беклозі, зміни після схвалення. Якщо проєкт уже працює на сервері, є ще й
перемикання: агент пише його кроки й міряє, скільки застосунок не працює, щоб ви спланували вікно;
старі дані видаляються лише після твого підтвердження.

### Новіший реліз або інший вибір

Режим `update`: лише те, що змінилося між релізами, за рішеннями, які вже є в реєстрі; він питає те,
що додав реліз, і пропонує переглянути ваші попередні відповіді. Щоб пройти весь
власний вибір (вимкнути stage, додати мутаційне тестування), налаштуйте проєкт заново: агент поставить
усі питання наново й приведе проєкт до нових відповідей.

### Перший раз на машині

`git clone … && cd … && make dev`. `make bootstrap` (його запускає `make dev`) створює `.env` з
`.env.example` (наявний `.env` лишається; команда називає, чого в ньому бракує), вмикає git-хуки й
створює зовнішні мережі. На хості нічого не встановлюється.

### Щоденна робота

`make dev` запускає стек (база, інструменти); `make run` запускає застосунок; `make shell` відкриває
shell з усіма інструментами; `make logs` показує логи наживо (`S=db` — один сервіс; `TAIL=200` —
останні рядки й вихід); `make seed` наповнює тестовими даними; `make migrate` застосовує нові
міграції; `make down` зупиняє на сьогодні (дані лишаються). Зміна коду не потребує перезбирання:
dev-образ перезбирається лише тоді, коли змінилися інструменти чи lock-файли (ENV-08). Щоб почати з
порожньої dev-бази, виконайте `docker compose -f docker-compose.dev.yml down -v` самі, потім `make dev`
і `make seed`; це видаляє dev-дані, тому агент без вашого дозволу його не запускає.

### Коли працює агент

Йому допомагають два хуки (AI-05, AI-06): після кожної правки файл перевіряється в dev-контейнері, і
червоне агент виправляє; перед кожною командою, що запустила б мовний інструмент на хості, хук
називає потрібну команду `make`. Правила для агента — в `AGENTS.md` проєкту.

### Відправити зміну

Шлях: робота в гілці, `git push` (ворота), `make verify`, злиття в `STAGE_BRANCH`, як заведено в
проєкті, `make stage` на stage-сервері; ніщо не розгортається саме по собі. Git-хук запускає `make gates` на
робочому дереві таким, яке воно є. У терміналі він перелічує незакомічені файли й питає `[y/N]`; без
терміналу (IDE, агент) друкує попередження й іде далі, тому агент спершу питає вас (правило — в
`AGENTS.md`). Червоні ворота — нічого не відправляється (QLT-02). Ворота працюють на вашій машині, тож
`--no-verify`, злиття у вебінтерфейсі, IDE без хуків чи клон без `make bootstrap` їх обминають; хто
хоче гарантії, додає CI, який викликає ті самі команди `make`
([відомі обмеження](standard/README.uk.md#відомі-обмеження)).

### Задачу закінчено

`make verify` — перед тим, як зміну зливають: усі перевірки (розділ 4).

### Перший сервер

Доступ на читання до репозиторію, клон, `.env` з `.env.example` (`chmod 600`, `PROJECT_ENV`, усі
`change-me` замінені, `DOCKER_GID`), фронтовий проксі (ваш власний TLS reverse proxy; проєкт його не містить), перший `make stage` / `make prod` (він збирає образи на
сервері); далі те, що ви обрали: копія бекапу поза сервером і heartbeat (`make restart` та `make backup-copy-check`) і монітор сервісу status.
Покроково: [operations](templates/project/docs/how-to/operations.md),
[backups](templates/project/docs/how-to/backups.md).

### Поставка на stage і prod

- **Stage:** `make stage` на stage-сервері. Відмовляється працювати на хибному клоні, у другій копії, локальних
  змінах чи залишеному `change-me`; за браку місця на диску попереджає й питає (без терміналу —
  `RISK=yes`); збирає те, чого бракує, мігрує, замінює
  лише змінене, записує коміт у `.deploy/history`, перевіряє налаштування (OPS-02). Кожен крок при
  збої зупиняє все (оцінка питає), а те, що працює, працює далі (ENV-09).
- **Prod:** спершу `make image-scan` на своїй машині (відомі вразливості в образах), потім зміна
  потрапляє в `PROD_BRANCH`, як заведено в проєкті, потім `make prod` на prod-сервері.
- **Hotfix:** робіть його як звичайну зміну в `STAGE_BRANCH` і пускайте через stage; коли prod не може
  чекати решту stage, відгалузьте від `PROD_BRANCH`, `make image-scan`, злийте в `PROD_BRANCH`,
  `make prod`, потім злийте `PROD_BRANCH` назад у `STAGE_BRANCH`.
- **Міграції** мусять працювати з попереднім релізом і бути безпечними при повторі; видаляйте чи
  перейменовуйте щось лише в релізі після того, який перестав це використовувати, інакше `make rollback`
  зламається.
- **Змінилося налаштування чи секрет:** змініть `.env` сервера, потім `make restart`. Змінений ліміт
  контейнера і похідні від нього числа йдуть разом, як пояснює `docs/how-to/tuning.md`.

### Після розгортання щось зламалось: `make rollback`

На сервері: повертає коміт, розгорнутий перед поточним, без міграцій. Гілка досі містить зламаний
коміт, тож наступний `make stage` / `make prod` розгорне його знову: спершу виправте його або зробіть
`git revert`. Деталі: [operations](templates/project/docs/how-to/operations.md).

### Що зараз працює

`make status`: середовище, коміт у робочій копії й останній розгорнутий коміт, здоров'я кожного сервісу. `make logs`
показує логи наживо. Зовнішній нагляд, якщо ви його обрали: OPS-04.

### Бекапи

На stage і prod сервіс `backup` працює сам (OPS-01): щодня перевірений набір кожної бази,
зашифрована копія поза сервером, ротація; щотижня пробне відновлення; після кожного вдалого дня пінг
на зовнішній монітор, щоб помітити й мертвий сервер. У dev сам нічого не запускається.

| Ви хочете | Команда |
|---|---|
| бекап зараз | `make backup` (`S=db` — одне сховище) |
| побачити набори й стан сервісу | `make backup-list`, `make backup-status` |
| довести, що відновлення працює | `make backup-drill` (`SET=<набір>` — цей набір) |
| перевірити копію поза сервером | `make backup-copy-check` |
| відновити дані | `make restore`: перевіряє набір, показує, що замінить, просить ввести ім'я бази; спершу робить страхувальний набір (`SET=before-restore` повертає до нього); на сервері зупиняє застосунок, а `make restart` запускає його знову |
| новий сервер із копії | ті самі паролі й `PROJECT_ENV`, потім `make restore FROM=copy SET=<набір> NO_SAFETY=1`, набір — із `make backup-list FROM=copy`: [backups](templates/project/docs/how-to/backups.md#a-new-server-from-the-off-server-copy) |

## 4. Перевірки

Два поверхи. **Базові команди** — єдине місце, де живе перевірка; кожну можна запустити окремо.
**Групові команди** нових перевірок не мають: запускають базові й закінчуються підсумком — рядок на
кожну базову (`ok`, `FAIL`, `off` або `skip` і останній рядок її виводу).

| Базова команда | Що запускає | Від чого захищає | У |
|---|---|---|---|
| `lint` | код не запускається: перевірка Dockerfile, форматування, лінтер, типи, shellcheck, посилання в документації (офлайн), контракти архітектури (R) | безладу в коді, помилок типів, мертвих посилань | gates, verify |
| `test` | код запускається, швидко й офлайн: юніт-тести, тести з реальною базою | зламаної логіки | gates, verify |
| `e2e` | запускається весь застосунок, повільно: контракт API, браузер | того, що видно лише повільними тестами | verify |
| `security` | секрети (gitleaks, офлайн), SAST, аудит залежностей (потрібна мережа) | ключів у git, небезпечного коду, відомих дір у бібліотеках | gates (лише скан секретів), verify |
| `infra` | `check-compose`, `parity`, `backup-test` | небезпечного чи розбіжного налаштування stage або prod | verify; `parity` і `check-compose` у кожному розгортанні |

- `make gates` = `lint` + `test` + скан секретів. Швидко, офлайн; його запускає pre-push-хук.
- `make verify` = `lint` + `test` + `e2e` + `security` + `infra`.
- Лише вручну: `make fix` (безпечні автоматичні виправлення, перед `make gates`), `make mutation-diff`
  і `make mutation` (тести, які нічого не ловлять; R, ваш вибір при налаштуванні), `make image-scan`
  (відомі вразливості в образах; образи лишаються на вашій машині).
- Кожне розгортання ще запускає `tuning-check`: кожен сервіс налаштований під свої ліміти (OPS-02).
- `LINT`, `TEST` і `SECRETS` обов'язкові: порожнє налаштування змушує команду відмовитися й валить групові команди; `off`
  записує, що проєкт цієї перевірки не хоче. Правила воріт: QLT-02. Коли запускається кожна
  перевірка: QLT-03.

## 5. Усі команди `make`

`make help` показує їх у цих групах. Де: **dev** ваша машина, **server** клон того сервера, **any**
кожен клон.

| Група | Команда | Де | Що робить |
|---|---|---|---|
| Dev | `dev` | dev | збирає змінене, запускає стек, мігрує (`NAME=<n>` — копія зі своїм стеком) |
| | `run`, `shell`, `seed`, `down` | dev | щоденна робота, вище |
| | `migrate` | dev | міграції (на сервері їх запускає `make stage` / `make prod`) |
| Checks | `lint`, `test`, `e2e`, `security`, `infra` | dev | базові команди, розділ 4 |
| | `gates`, `verify` | dev | групові команди, розділ 4 |
| | `fix`, `mutation`, `mutation-diff`, `image-scan` | dev | лише вручну |
| Servers | `stage`, `prod` | свій сервер | оновлення до гілки, збирання, міграції, розгортання |
| | `rollback`, `restart` | сервер | попередній розгорнутий коміт; застосувати змінений `.env` |
| | `images` | сервер | зібрати й стягнути образи, нічого не запускаючи (переведення запущеного проєкту на стандарт) |
| | `tuning-check` | сервер | запущені налаштування проти очікуваних |
| Any clone | `status`, `logs` | any | що працює і наскільки здорове; логи |
| Backups | `backup`, `backup-list`, `backup-drill`, `backup-status`, `restore` | any | розділ 3 |
| | `backup-copy-check` | server | перевірити копію поза сервером |
| | `backup-test` | dev | тестовий бекап і пробне відновлення dev-бази |
| Service | `help`, `bootstrap`, `parity`, `check-compose` | any | список; підготувати клон; файли stage і prod: однакові й за правилами |

Власні команди проєкту (`MIGRATE`, `LINT`, `TEST`, `RUN` тощо) — це налаштування вгорі `Makefile`.
Свої цілі проєкт додає лише в блок «Project targets» (ENV-05), і `make help` показує їх у групі
«This project».
