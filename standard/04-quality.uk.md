# Інструменти якості

> Версія 1.0.0-draft · Українська · [English](04-quality.md)

### QLT-01. Категорії інструментів (M)

Стандарт задає категорії, а не назви: назви в таблиці — типовий вибір для кожної мови
([D-0026](../decisions/0026-quality-tools.uk.md)). Інший інструмент тієї самої категорії
допустимий, якщо він записаний у реєстрі з причиною. Версії, а також те, чому версію вибрано чи
виключено, — у D-0026; піни лежать в образах і lock-файлах проєкту.

| Категорія | Рівень | Python | TypeScript / React | PHP | Де | Команда |
|---|---|---|---|---|---|---|
| Формат | M | ruff format | prettier | php-cs-fixer | dev | `lint` |
| Lint | M | ruff (з S, PL, C90, B, …) | eslint (+ typescript-eslint, react-hooks) | phpstan / psalm + rector `--dry-run` | dev | `lint` |
| Типи | M | pyright strict | tsc strict + `noUncheckedIndexedAccess` | phpstan max | dev | `lint` |
| Shell-lint | M, якщо є `*.sh` | shellcheck над усіма скриптами в git | те саме | те саме | dev | `lint` |
| Посилання в документації | R | lychee `--offline` | те саме | те саме | dev | `lint` |
| Архітектурні контракти | R (≥3 пакети) | import-linter | eslint-plugin-boundaries / dependency-cruiser | deptrac | dev | `lint` |
| Перевірка Dockerfile | R | `docker build --check` над Dockerfile кожного власного образу | те саме | те саме | хост | `lint` |
| Тести без мережі | M | pytest | vitest | phpunit | dev | `test` |
| Тести на справжній БД | R | pytest проти реального Postgres (tmpfs) | | | dev | `test` |
| Тести властивостей (property-based) | O (де є «весь домен входів») | hypothesis | fast-check | | dev | `test`, якщо є |
| API-контракт | R, якщо є OpenAPI | schemathesis | генерований клієнт з OpenAPI | | dev | `e2e` |
| Наскрізні тести в браузері | R, якщо є UI | Playwright у dev-образі | Playwright | | dev | `e2e` |
| Секрети | M | gitleaks (пін, без мережі) | те саме | те саме | dev | `security`, а також `gates` |
| SAST | R | semgrep (`--metrics off`, правила з локальних файлів) | semgrep | semgrep / psalm taint | dev | `security` |
| Аудит залежностей | M | pip-audit | npm audit | composer audit | dev, мережа | `security` |
| Скан образів | M, якщо є prod | trivy image | те саме | те саме | dev, мережа | `image-scan` |
| Автоматичні виправлення | R | ruff format + `ruff check --fix --no-unsafe-fixes` | prettier `--write` + `eslint --fix` | `php-cs-fixer fix --allow-risky=no` | dev | `fix` |
| Мутаційне тестування | R, на вибір власника | cosmic-ray + мутанти, написані вручну, для перевірок безпеки | StrykerJS | Infection | dev, власний контейнер з лімітами `MUTATION_CPUS` / `MUTATION_MEM` | `mutation`, `mutation-diff` |
| Покриття | O (діагностика по diff) | coverage.py | vitest --coverage | pcov | dev | — |

«dev» означає dev-контейнер, у якому немає власного Docker; «хост» — власний Docker машини, до
якого dev-контейнер не дістає. Стовпець «Команда» — це базова команда, що виконує категорію
([QLT-03](#qlt-03-коли-запускається-кожна-перевірка-m)). Правила semgrep — файли проєкту: проєкт
ніколи не поширює копій правил реєстру, які підтримує Semgrep, бо їхня ліцензія дозволяє лише
внутрішнє використання в бізнесі. `gitleaks dir` читає кожен файл робочого дерева, також ті, які
ігнорує git (`.env`, кеші, результати збирання), тож проєкт дає gitleaks їхній allowlist у
`.gitleaks.toml`, як це робить для своїх зразків
[`tests/stacks/.gitleaks.toml`](../tests/stacks/.gitleaks.toml); `.env.example` лежить у git і
лишається в скані.

Мутаційне тестування власник обирає, коли застосовують стандарт: питають `prompt/new.md` і
`prompt/adopt.md`. «Так» додає сервіс `mutation`, його команди й налаштування, інструмент мови та
доказ; «ні» не додає нічого з цього, а вибір іде в реєстр.

`make image-scan` збирає власні образи коміту, на якому стоїть клон, на хості так само, як їх
збирає сервер ([ENV-09](02-environments.uk.md#env-09-поставка-розгортання-і-відкат-m-якщо-є-stage-або-prod)),
а trivy в dev-контейнері сканує кожен із них; він називає кожен образ, що не пройшов. Типовий
базовий образ має багато знахідок (датована кількість — у
[D-0020](../decisions/0020-one-way-of-working.uk.md)), тож скан усіх рівнів завжди червоний:
`trivy.yaml` із шаблону падає на знахідках CRITICAL, для яких є виправлення, проєкт посилює його,
коли може (додає HIGH, потім прибирає `ignore-unfixed`), а знахідка, яку він приймає, потрапляє в
`.trivyignore` з причиною. Скан завантажує базу trivy, тож потребує мережі, а образи, які він
збирає, лишаються на машині. Його рівень — M скрізь, де є prod, однаковий в ENV-09 і QLT-03: зміна
потрапляє в `PROD_BRANCH` лише після того, як скан на ній пройшов.

`make fix` запускає виправлялки тих самих інструментів у безпечному режимі: для ruff і
php-cs-fixer — виправлення й правила, які сам інструмент не вважає небезпечними чи ризикованими;
rector лишається в `--dry-run`, бо він рефакторить код, а його зміни читають як diff. Команду
запускають вручну, людина чи агент, ніколи не ворота й не хук, бо ворота лише перевіряють (QLT-02).
Виправлялка міняє вигляд коду і, за визначенням самого інструмента, не те, що код робить; жодна не
гарантує цього, тож після `make fix` перегляньте `git diff` і запустіть `make gates`. Сенс у тому,
що програма робить прості правки миттєво й щоразу однаково, а агент береться лише за те, чого
програма не вміє ([D-0026](../decisions/0026-quality-tools.uk.md) має джерела).

Кожен інструмент мутаційного тестування за замовчуванням мутує весь код. Тож `MUTATION_DIFF` — це
команда проєкту, і базу для `make mutation-diff` вона називає сама, зазвичай stage-гілку такою,
якою її має клон (`origin/<stage-гілка>`: спершу `git fetch`, якщо вона могла застаріти); формам
для PHP і Python потрібен git у dev-образі ([D-0020](../decisions/0020-one-way-of-working.uk.md)):
- PHP, Infection: `infection --git-diff-lines --git-diff-base=origin/$(STAGE_BRANCH)` (make
  підставляє `$(STAGE_BRANCH)` у налаштуванні) мутує лише змінені рядки; база за замовчуванням —
  `master`.
- Python, cosmic-ray: після `cosmic-ray init <config> <session>` команда `cr-filter-git --config
  <config> <session>` пропускає кожну мутацію поза рядками, зміненими відносно `branch` із
  `[cosmic-ray.filters.git-filter]` конфігу (за замовчуванням `master`; за stage-гілкою він не
  йде, тож задайте `origin/<stage-гілка>` і міняйте обидва разом), а `cosmic-ray exec <config>
  <session>` запускає мутації, які ще не мають результату.
- TypeScript, StrykerJS: режиму git немає; `--incremental` порівнює код і тести з власним
  попереднім звітом (`reports/stryker-incremental.json`; `--incrementalFile` переносить його,
  наприклад, у `.cache/`) і тестує лише змінений код. База — попередній запуск: перший запуск без
  звіту (новий клон, нова робоча копія, очищена тека) мутує весь код. Змін у снапшотах,
  залежностях чи змінних середовища він не бачить.

### QLT-02. Правила воріт (M)

- Ворота лише перевіряють: форматер чи фіксер працює в режимі перевірки й ніколи не переписує
  файли; якщо ворота змінюють файл, хук pre-push відхиляє push.
- Кожен інструмент воріт має пін точної версії в образі або lock-файлі. Інструмент, який потрапляє
  в образ як бінарний файл або з іншого образу (як-от gitleaks, lychee, trivy), закріплений за
  версією і за digest образу чи контрольною сумою, ніколи лише за тегом
  ([D-0026](../decisions/0026-quality-tools.uk.md)).
- Жоден мережевий інструмент не входить у `gates`; мережеві перевірки — у `verify` і `image-scan`.
  Lint, тести й скан секретів працюють у dev-контейнері й не потребують мережі, щойно образ
  зібрано. Перевірка Dockerfile в `lint` — єдиний крок на хості: коли базового образу на машині
  немає, `docker build --check` може звертатися до реєстру образу, щоб прочитати його метадані
  (D-0026).
- Три перевірки — обов'язкові налаштування проєкту: lint (`LINT`), тести (`TEST`) і скан секретів
  (`SECRETS`). Порожнє налаштування (ще не задано) — це збій, а не успіх: його команда
  відмовляється запускатися, а `make gates` і `make verify` завершуються FAIL. Проєкт, який не
  хоче перевірки, пише `off`: це записаний вибір власника (його питають, коли застосовують
  стандарт, і записують у реєстр), і в підсумку це видно як `off`. Налаштування e2e (`E2E`) і
  безпеки (`SECURITY`) можуть лишатися порожніми (у підсумку `skip`) або бути `off`.
- `gates` містить лише швидкі перевірки й завершується за кілька хвилин на машині розробника
  (орієнтир — до п'яти); повільніша перевірка переходить у `verify`. Надто повільні ворота
  пропускають, а пропущені ворота нічого не перевіряють.
- `make gates` і `make verify` запускають кожну базову команду, також після того, як попередня
  впала, і завершуються підсумком — по рядку на кожну базову команду: `ok`, `FAIL`, `off` або
  `skip` і останній змістовний рядок її виводу (першого кроку, що впав, коли кроків кілька).
  Агент наводить його й
  вважає задачу готовою, лише коли `make gates` зелений ([AI-01](05-agents.uk.md)).
- Git-хук `pre-push` із [`templates/project/.githooks/`](../templates/project/.githooks/pre-push)
  запускає `make gates` у робочому дереві, яке має містити коміт, що пушиться; якщо ворота
  падають, git нічого не пушить. Ворота бачать файли такими, як вони є, разом з
  незакоміченими змінами, і хук їх не ховає: у терміналі він їх перелічує й питає, чи нічого не
  забули закомітити, і далі йде лише «так» (`y`); де спитати не може (IDE, агент, скрипт), він друкує
  список як попередження й іде далі. Він не відрізняє агента від людини: агент питає власника в
  сесії, перш ніж пушити з незакоміченими змінами ([AI-01](05-agents.uk.md)). Push гілки чи тегу, чий вміст відрізняється від коміту, на якому
  стоїть клон, відхиляється, бо ворота перевіряють лише цей коміт; так само відхиляється push, під
  час воріт якого зсунувся `HEAD` або змінився файл (ворота, що переписали файл, або ваша
  власна правка за цей час: запустіть push ще раз). Хук ніколи не користується `git stash`. Хук
  встановлює `make bootstrap` (`git config core.hooksPath .githooks`), бо git не копіює хуки разом
  із клоном. `git push --no-verify` його пропускає — лише для надзвичайних випадків; коли ним може
  користуватися агент, сказано в [AI-01](05-agents.uk.md).
- Ворота локальні, і push може їх обійти: `git push --no-verify`, злиття у веб-інтерфейсі, IDE чи
  інший клієнт, що не запускає хуків, клон, де `make bootstrap` не запускали. Хто хоче гарантії,
  додає власний CI; він викликає ті самі команди `make` (`gates`, `verify`) і не повторює
  перевірок своїми словами. Стандарт CI не додає.

### QLT-03. Коли запускається кожна перевірка (M)

Базові команди запускають перевірки однієї галузі й не містять жодної іншої базової команди;
групові команди нових перевірок не мають, але `gates` запускає лише крок `SECRETS` команди `security` (його рядок
підсумку — `secrets`). Команда, що змінює файли чи триває довго, запускається вручну й не входить
у жодну групу.

| Команда | Вид | Що запускає | Чому саме тут |
|---|---|---|---|
| `lint` | базова | код не запускається: спершу перевірка Dockerfile, потім перевірка формату, lint, типи, shell-lint, посилання в документації, архітектурні контракти | швидко; працює без мережі в dev-контейнері, крім перевірки Dockerfile на хості |
| `test` | базова | код запускається, швидко, без мережі: юніт-тести, тести на справжній БД, тести властивостей | швидко й без мережі, тож безпечно на кожен push |
| `e2e` | базова | запускається весь застосунок, повільно: API-контракт, браузер і виклики зовнішніх API, де вони є в проєкті | повільно, а мережа може знадобитися |
| `security` | базова | скан секретів (крок `SECRETS`), потім SAST і аудит залежностей | аудиту потрібна мережа |
| `infra` | базова | `check-compose`, `parity` і тестовий бекап, де в проєкті є бекап; перші дві ще й у кожному розгортанні | потрібен Docker, і це триває, тож вони не входять у `gates` |
| `gates` | групова | `lint`, `test` і крок `SECRETS` команди `security` (рядок підсумку `secrets`) | швидка частина без мережі: перед кожним push |
| `verify` | групова | `lint`, `test`, `e2e`, `security` і `infra` | усе, коли задачу завершено |
| `fix` | вручну | автоматичні виправлялки в безпечному режимі | вона змінює файли, чого ворота робити не повинні |
| `mutation`, `mutation-diff` | вручну | мутаційне тестування всього коду чи зміненого | повільно, і працює у власному контейнері |
| `image-scan` | вручну | власні образи коміту, на якому стоїть клон, зібрані й проскановані | збирає образи, потребує мережі й диска, а нові вразливості з'являються й без змін коду |

| Коли | Що | Хто запускає |
|---|---|---|
| після кожної правки агента | формат, lint і, де можливо, типи цього файла ([AI-05](05-agents.uk.md)) | хук агента, сам |
| перед кожним `git push` | `make gates` | git-хук, сам |
| коли задачу завершено, до її злиття | `make verify` | розробник або агент |
| перед злиттям зміни в `PROD_BRANCH` | `make image-scan` (збирає образи коміту, на якому стоїть клон, і сканує їх) | розробник або агент |
| кожні `STATUS_PUSH_INTERVAL` | стан кожного сервісу та вільне місце диска Docker і теки бекапів, що надсилаються монітору ([OPS-04](03-operations.uk.md)) | сервіс `status`, сам |
| щодня, а щотижня ще й пробне відновлення | набір, копія і пробне відновлення сервісу `backup` ([OPS-01](03-operations.uk.md)) | сервіс `backup`, сам |
| перед злиттям великої зміни | `make mutation-diff` (змінений код) або `make mutation` (увесь код), коли потрібна повна картина; там, де власник обрав мутаційне тестування | розробник або агент |
| коли ворота падають на форматуванні чи простих зауваженнях lint | `make fix`, потім `git diff` і `make gates`; агент запускає її, перш ніж правити таке вручну | розробник або агент |

README проєкту містить другу таблицю в першому розділі
([DOC-04](06-docs.uk.md#doc-04-робота-з-цим-проєктом-m)), без рядків, що не стосуються проєкту
(немає хука [AI-05](05-agents.uk.md), бекапу, сервісу status, prod, мутаційного тестування), а `AGENTS.md`
посилається на неї, тож агент теж за нею діє.
