# Документація і реєстр

> Версія 1.0.0-draft · Українська · [English](06-docs.md)

### DOC-01. Склад документації (M)

Документація ділиться за Diátaxis (навчання, інструкції, довідка, пояснення), а рішення — за ADR
(один файл — одне рішення). Якою мовою писати документацію, вирішує проєкт. Обов'язкові сторінки:

| Сторінка | Що в ній | Коли обов'язкова |
|---|---|---|
| `README.md` | починається з розділу «Working with this project» ([DOC-04](#doc-04-робота-з-цим-проєктом-m)) | завжди |
| `docs/how-to/operations.md` | інструкція для сервера (runbook): кожен серверний сценарій із DOC-04 | є stage або prod |
| `docs/how-to/backups.md` | як працює бекап, як налаштувати й перевірити копію поза сервером, як перевірити відновлення і як відновити | є бекап ([OPS-01](03-operations.uk.md)) |
| `docs/how-to/tuning.md` | кожен налаштований параметр: що, навіщо, як рахується, як змінити, як перевірити, джерело | є stage або prod ([OPS-02](03-operations.uk.md)) |
| `docs/reference/project-registry.md` | реєстр складових ([DOC-03](#doc-03-реєстр-складових-m)) | завжди |
| `docs/adr/` | архітектурні рішення проєкту | з першого рішення |

### DOC-02. Беклог і стан сесій (M)

Беклог задач — в одному місці: файл у репо або трекер задач. Стан сесій плагіна робочого циклу
лишається поза git ([AI-03](05-agents.uk.md)). Ні те, ні інше не дублює `docs/`.

### DOC-03. Реєстр складових (M)

`docs/reference/project-registry.md` — один короткий файл, який каже те, чого не скажуть файли:
навіщо є кожна складова, що зберігає дані й потрапляє в бекап, відповіді власника на питання, задані
під час застосування стандарту, і де проєкт відступає від стандарту. Це **точка входу**, а не
копія: версії, стадії образів, піни й налаштування живуть лише у своїх файлах, а кожен рядок
посилається на файл, що визначає складову. Тож підвищення версії змінює лише той файл
([PRN-05](01-principles.uk.md)). Те, що файли вже показують, не повторюється: цілі інструментів
якості — в `Makefile`, хуки й скіли агента — в його власній теці, список документів — у `docs/`;
аудит щоразу рахує їх наново.

```markdown
# Project registry — <project name>

Standard: <version, for example v1.0.0> · Last reconciled: <date, commit>

## 0. Profile and decisions
Type: service | library | frontend | pipeline | ML · Languages: … · Environments: dev, [stage], [prod]
| ID | Answer | Why | Date |

## A. Components and tools | Component | Defined in | Problem it solves | Environments | Persistent? Backed up? |

## E. Deviations from the standard | Rule (ID) | Deviation | Reason | ADR | What removes it |
```

Розділи зберігають літери 0, A і E, щоб кожне посилання на «розділ E» лишалося чинним. Інших
колонок не додається; якщо треба більше, це посилання на сторінку довідки.

- **Розділ 0** — місце відповідей власника: один рядок на кожну відповідь, з її ID (`S-nn`
  для питання [TYP-01](07-project-types.uk.md#the-choices); для відповіді поза ними — коротка назва,
  як-от `name`, `scope` чи `data stores`, або рішення власника за аудитом, назване його знахідкою),
  відповіддю (увімкнено
  чи вимкнено, або значення: команда, тека, гілка), причиною і датою; `S-01` і `S-02` — це рядок
  профілю над нею. Частина, від якої власник
  відмовився, — рядок тут, а не відступ у розділі E. Оновлення читає ці відповіді й не питає знову;
  воно питає лише про те, що новий реліз додав після того, як їх дали, а потім пропонує по одній
  переглянути попередні відповіді ([`prompt/update.md`](../prompt/update.md)). Щоб пройти всі,
  власник налаштовує проєкт заново ([`prompt/start.md`](../prompt/start.md)): це ставить усі питання
  наново, з
  поточними відповідями як довідкою, і приводить проєкт до нових відповідей, додаючи або прибираючи
  частини.
- **Розділ A** перелічує кожну складову та кожен інструмент із проблемою, яку він вирішує
  ([PRN-06](01-principles.uk.md)); рядок каже, чи складова зберігає дані й чи потрапляє в бекап.
- **Розділ E** перелічує кожен відступ із тим, що його знімає ([PRN-09](01-principles.uk.md)).

Поле `Standard` у шапці — версія стандарту, за якою проєкт звірено востаннє; з неї починається
оновлення до нової версії.

### DOC-04. Робота з цим проєктом (M)

README кожного проєкту починається з розділу «Working with this project» (робота з цим проєктом),
взятого з [`templates/project/README.md`](../templates/project/README.md) з підставленими назвами
проєкту (перекладеного, якщо документація проєкту не англійською; команди лишаються як є, а
посилання на цей розділ в `AGENTS.md` і `docs/how-to/operations.md` ідуть за його заголовком). Він
містить дві таблиці й нічого проєктного, крім назв і адрес:

1. **Яка команда в якій ситуації**: для кожного сценарію нижче, що стосується проєкту, — команда,
   що вона робить, що буває, коли щось іде не так, і що тоді робити.
   - перший раз на машині; щоденна розробка й запуск застосунку (`make dev`, `make run`);
     змінилися залежності чи Dockerfile; тестові дані; друга копія для паралельної роботи;
   - перед push; прості зауваження перевірок (`make fix`); один вид перевірки; завершення задачі
     (`make verify`);
   - поставка зміни на stage (`make stage`); перевірка образів перед prod (`make image-scan`);
     розгортання в prod; змінене значення в `.env` сервера (`make restart`); відкат; перегляд
     того, що запущено і чи воно здорове; сповіщення, коли щось іде не так (сервіс status,
     [OPS-04](03-operations.uk.md));
   - бекап зараз і перевірка відновлення (`make backup`, `make backup-drill`); які набори є і стан
     бекапів (`make backup-list`, `make backup-status`); відновлення даних (`make restore`);
     налаштування чи зміна копії поза сервером (`make backup-copy-check`)
     ([OPS-01](03-operations.uk.md));
   - кожна власна команда проєкту з блоку `Makefile` «Project targets»
     ([ENV-05](02-environments.uk.md#env-05-цілі-make-m)).

   Сценарій чи перевірка, яку власник вимкнув у розділі 0 реєстру (мутаційне тестування, нагляд за
   станом, перевірка, задана як `off`, stage чи prod, яких немає), рядка не має: проєкт прибирає її з обох
   таблиць.
2. **Коли запускається кожна перевірка** ([QLT-03](04-quality.uk.md)).

`docs/how-to/operations.md` — повна інструкція для сервера (runbook) з тієї самої теки шаблонів,
де кожен із цих сценаріїв розписано крок за кроком: перший сервер з нуля (доступ на читання до
репо, клон, `.env`, `PROJECT_ENV`, фронт-проксі, перший `make stage` / `make prod`, який збирає
образи на сервері); оновлення; перенесення stage у prod; одна копія кожного середовища на машині;
невдала збірка образу; невдала міграція; контейнер, що не стає healthy; відкат; перезавантаження
сервера; заповнений диск; логи замінених контейнерів; змінений секрет чи інше значення `.env`
(`make restart`); нагляд за станом ([OPS-04](03-operations.uk.md)); перевірка й відновлення
бекапу; переїзд на новий сервер з копії поза сервером перед першим `make stage` / `make prod`.
