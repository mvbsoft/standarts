# Принципи

> Версія 1.0.0-draft · Українська · [English](01-principles.md)

## Аксіоми

### PRN-01. Усе в Docker (M)

Проєкт піднімається на голому сервері з контейнерів. На хості є лише інструменти нижче. Це єдиний
перелік хостових інструментів: інші документи посилаються сюди, а не повторюють його.

| Інструмент | Машина розробника | Сервер (stage, prod) |
|---|---|---|
| Docker Engine 25.0 або новіший (healthcheck-и використовують `start_interval`) і плагін Docker Compose (`docker compose`), перевірено з Compose v5.5.0 | так | так |
| Docker Buildx, для збірок, що використовують build-секрети або `RUN --mount`; 0.15.0 або новіший там, де `make lint` запускає `docker build --check` | так | так |
| `git` 2.31 або новіший (скрипти використовують `git rev-parse --path-format`) | так | так |
| `make`, POSIX `sh`, `ps` з procps, `stat` з GNU coreutils і `tar` (`sh` запускає цілі `make`, хуки й лаунчер мовних серверів) | так | так |
| агент для кодування (Claude Code, єдиний підтримуваний поки що, [05-agents](05-agents.uk.md)); Node.js, лише якщо його вимагає глобальний плагін Claude Code | так | ні |
| `gh`, для pull request-ів та issues на GitHub (O; жоден шаблон чи промпт його не викликає) | якщо використовується | ні |

Будь-яке інше виконання на хості — виняток за [PRN-09](#prn-09-винятки-m), записаний у розділі E
реєстру з причиною.

Джерела мінімальних версій: довідка Dockerfile, “This option requires Docker Engine version 25.0 or later.” ([start interval](https://docs.docker.com/reference/dockerfile/#healthcheck)); сторінка перевірок збірки Docker, “Buildx version 0.15.0 and later” ([checks](https://docs.docker.com/build/checks/)); нотатки до Git 2.31.0, “`git rev-parse` can be explicitly told to give output as absolute” або relative “with the `--path-format=(absolute|relative)` option” ([notes](https://raw.githubusercontent.com/git/git/master/Documentation/RelNotes/2.31.0.adoc)).

### PRN-02. Один файл — одне середовище (M)

`docker-compose.dev.yml` = dev, `docker-compose.stage.yml` = stage, `docker-compose.prod.yml` =
prod; `docker-compose.<роль>.yml` — для спеціальних ролей (наприклад `agents`). Файла з типовим
ім'ям (`compose.yaml`, `compose.yml`, `docker-compose.yaml`, `docker-compose.yml`) і жодного
`*.override.*` немає ні в репо, ні в батьківських теках, тож голий `docker compose up` падає і
нічого не стартує. Файл обирається лише явним `-f`; люди роблять це через `make`. `COMPOSE_FILE`,
`COMPOSE_PROJECT_NAME` і `COMPOSE_PROFILES` не задаються ніде: ні в `.env`, ні в `.env.example`, ні
в shell-профілі (`COMPOSE_PROJECT_NAME` перекриває `name:` файла, `COMPOSE_PROFILES` запускає
сервіси, які профіль тримає вимкненими, `COMPOSE_FILE` обирає файл щоразу, коли `-f` пропущено).
Кожен файл має власний `name:`.

### PRN-03. Stage і prod запускають образи того самого вмісту (M)

Код запечений в образ. Кожен власний образ проєкту збирається на сервері, який його запускає,
командою `make stage` / `make prod`, із закомічених файлів коміту, що розгортається, і отримує тег —
git-хеш дерева (tree hash) цього коміту; реєстру образів немає
([ENV-09](02-environments.uk.md#env-09-поставка-розгортання-і-відкат-m-якщо-є-stage-або-prod),
[D-0025](../decisions/0025-images-built-on-the-server.uk.md)). Коміти з однаковим вмістом мають
однаковий хеш дерева, тож сервер збирає образ один раз і далі використовує його. Stage і prod
збирають той самий вміст: кожен сторонній образ у файлах stage і prod та кожен базовий образ у
Dockerfile-ах власних образів закріплений за версією й digest, що перевіряє `make check-compose`
([ENV-03](02-environments.uk.md#env-03-перевірка-правил-compose-m-якщо-є-stage-або-prod)), а
залежності ставляться з lock-файлів. Це робить дві збірки однаковими за вмістом, хоча й не байт у
байт: пакети, які збірка ставить із репозиторіїв операційної системи, усе ж можуть відрізнятися
([відомі обмеження](README.uk.md#відомі-обмеження)). Stage і prod відрізняються лише
конфігурацією через env-файл сервера.

### PRN-04. Fail closed (M)

Секрети не мають значень за замовчуванням (`${X:?}`). `.env` сервера й файл build-секретів може
читати лише їхній власник, а розгортання інакше відмовляється. Healthcheck перевіряє сервіс з
автентифікацією. Ворота не зеленіють, якщо не запускалися.

### PRN-05. Зроблено = тести + документація + реєстр (M)

Зміна йде разом зі своїми тестами й документацією, яку вона зачіпає. Зміна, що додає чи прибирає
складову або інструмент, змінює причину, з якої вони є, змінює те, що потрапляє в бекап, змінює
відповідь власника або додає відступ, оновлює реєстр складових (`docs/reference/project-registry.md`,
[DOC-03](06-docs.uk.md#doc-03-реєстр-складових-m)) у тому самому коміті. Підвищення версії змінює
лише файл, у якому ця версія записана.

### PRN-06. Нічого «про запас» (M)

Інструмент додається лише під конкретну проблему, і ця проблема записана в реєстрі.

## Репо і машина

### PRN-07. Репо самодостатнє (M)

Клон репо + Docker + `make bootstrap` — і все працює в будь-якій теці на будь-якій машині. У
файлах git немає шляхів у сусідні репо (`../інший-репо/…`) чи абсолютних шляхів машини
(`/home/…`, `C:\…`), і скрипти не викликають код іншого репо напряму. Спільне між репо
передається лише версійно: образом Docker з тегом, пакетом у lock-файлі або плагіном за
git-джерелом. Якщо dev-боксу потрібен код сусіднього репо для читання, його шлях задає змінна в
`.env`, а без неї проєкт усе одно стартує.

### PRN-08. Що глобально, що в проєкті (M)

| Глобально (машина чи акаунт) | У проєкті |
|---|---|
| глобальні плагіни Claude Code; `~/.claude/CLAUDE.md`; режим дозволів, модель, effort; marketplaces як git-джерела, а не абсолютні шляхи в чужий репо; інструменти хоста з PRN-01 | compose-файли, Dockerfile-и, `Makefile`, lock-файли, `.env.example`; проєктні скіли, команди й хуки; закріплені `enabledPlugins`; реєстр |
| нічого проєктного: жодних `~/.claude/skills/` для конкретного репо | нічого машинного: жодних абсолютних шляхів у файлах git; шлях до робочої теки — лише змінною з дефолтом |

### PRN-09. Винятки (M)

Виняток зі стандарту допустимий, лише якщо одночасно:
1. він записаний у розділі E реєстру з причиною;
2. є ADR, якщо виняток змінює архітектурне рішення;
3. вказано, що його знімає (подія або дата).

Хостові винятки перелічені лише там; `AGENTS.md` посилається на цей розділ, а не повторює його.
«Так історично склалося» — не причина.

### PRN-10. З кожним проєктом працюють однаково (M)

Незалежно від мови, кожен проєкт налаштовують, розробляють, перевіряють, поставляють, розгортають і
відкочують тими самими цілями `make` ([ENV-05](02-environments.uk.md#env-05-цілі-make-m)), а його
README починається з того самого розділу, який каже, яку команду запускати в якій ситуації
([DOC-04](06-docs.uk.md#doc-04-робота-з-цим-проєктом-m)). Хто знає один проєкт, знає, як працювати
з будь-яким іншим; те, чим проєкти відрізняються, живе в кількох названих налаштуваннях, а не в
іншому способі роботи.
