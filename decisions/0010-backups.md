# D-0010. One backup service per project, proven by restore drills and an off-server copy the server cannot erase

> English · [Українська](0010-backups.uk.md)

**Status:** accepted · **Date:** 2026-10-18 · **Rules:** OPS-01

## Context

Most projects had no backup at all. A backup that was never restored is a hope, not a backup, and a backup on the same disk does not survive that disk. A copy elsewhere that the server itself may delete does not survive someone who breaks into the server either, and a restore that replaces data without asking can destroy the state it was meant to repair.

## Decision

Every store keeps its data in a named volume declared in the compose file; only `docker compose down -v`, `docker volume rm` and `docker volume prune -a` delete it (and so does deleting Docker's own data: uninstalling Docker Desktop, resetting its disk image, or removing `/var/lib/docker` on a Linux host), and no `make` target runs them; an agent runs `down -v` only for its own proof copy.

One `backup` service, built from the standard's template ([`templates/project/docker/backup/`](../templates/project/docker/backup/)), holds all backup logic for every store of the project, one module per store. The standard sets the module's interface (make a set from one consistent state with the facts the restored store must match, check it, drill it into a temporary server, restore it into the working store, name the store a person confirms with); the template ships a Postgres module as an example (PostgreSQL 15 or later), and the project writes the module of each other store after it. Before each backup the service creates its own read-only role, never the superuser, or brings the role's rights up to date, and dumps as that role; the dump and the manifest's row counts read one snapshot. The application too connects as a role of its own and never as the superuser, whose password only the database service and `backup` use (the template's health check of the database creates the role and keeps its password). What may differ between servers is a variable in `.env`; what makes the service what it is (its stores, its user, its mounts) is in the compose files and the Dockerfile.

On stage and prod it writes checked sets with a manifest to the host folder `BACKUP_DIR` (`/backup` inside the container, fixed) as `<service>/<UTC time>/`; the folder is the owner's choice when the standard is applied (the template's default is `docker/backup/data`, in `.gitignore` and `.dockerignore`), one per environment and project, and the service takes it only when it is empty, missing, marked as its own, or holds only the sets an earlier release of the service made. In dev, where the sets are test sets, they go to the named volume `backup-data`, so no folder owned by the container's user stays in a clone. It restores the newest set into a temporary database inside itself once a week, and keeps on the server the newest set of each of the last `BACKUP_KEEP_DAILY` days and `BACKUP_KEEP_WEEKLY` ISO weeks.

When `BACKUP_COPY_TO` names a restic repository on a rest-server (`rest:https://<host>:<port>/<login>/`), every checked set is also copied there with restic, which encrypts it with the password `BACKUP_COPY_PASSWORD`: each set is tagged with its service under a static host name, and the repository is created on first use. The rest-server runs in append-only mode (`--append-only --private-repos`), so the server's login can add and read sets and can neither delete nor change one; the service never runs `forget`, `prune` or any command that rewrites a snapshot. The storage side rotates the copy with a login of its own: `restic forget --group-by host,tags` with the same daily and weekly counts, `--keep-within 7d`, and the safety sets kept apart, then `prune`. The guarantee has a limit: because restic counts only days and weeks that have a set (quoted in Sources), sets dated in the future can use up the daily and weekly counts, so what is certain against a broken-into server is the last window; the storage side has to remove future-dated sets itself. A copy into a local folder or over `rest:http://` is accepted for tests only and is an audit finding in prod. Once a week (`BACKUP_DRILL_DAY`) the service runs `restic check --read-data-subset` on the copy (`BACKUP_COPY_READ`, 10% by default); a failure is notified and makes the service unhealthy. `make backup-copy-check` proves the copy after setup: it writes a test set, reads it back, tries to delete it and fails if it can, runs the read check, and prints `OK` or the exact reason. The standard says only what the copy must do (the server may add and read, never delete or change; the storage side rotates; the server reads it back), so another store (object storage with keys that cannot delete, for example) is the project's choice with its own setup and proof.

`make restore` checks the set of every store first and shows what it would replace. In a terminal the warning is red and the person types the name of each database; without one only `CONFIRM=yes` on make's command line confirms (a `CONFIRM=yes` from the environment, `MAKEFLAGS` or a parent make is refused). Before it replaces a store it makes a safety set of it as it is, `before-restore-<UTC time>`: an ordinary set, copied off the server, at most one per store on the server (none before the first restore), ignored by rotation, `latest` and the weekly drill, taken by `SET=before-restore` or its full name for a restore or for `make backup-drill`; `NO_SAFETY=1` skips it. The storage side keeps the newest safety set and, with `--keep-within 7d`, every one of the last seven days. With `FROM=copy` it is also how a new server gets its data. `S=<service>` limits backup, drill, list, restore and `backup-test` to one store. On a server deploy that runs a migration (not on a clone's first deploy, when nothing was deployed from it yet), a fresh set is made right before the migration step; if that backup, or only its off-server copy, fails, the command says which part and that the migration would run without a fresh set off the server, or anywhere when the local set failed, and asks. A backup or restore finds before it writes whether the disk of the backup folder has room for the new sets plus `DISK_RESERVE`, and a drill whether `/drill` has room for the set's size plus `DISK_RESERVE`. These are estimates: the command explains what it found and asks (y/N in a terminal; without one it refuses until `RISK=yes` is on make's command line), while the service's own scheduled jobs have no one to ask and still refuse.

The healthcheck turns unhealthy when the newest set or off-server copy is older than `BACKUP_MAX_AGE`, or the last drill or read check failed; a deploy then prints a warning and still runs. The service starts as root only to give its folders to the database user and then drops to it; that is the template's only exception to non-root and to `cap_drop: ALL` (it adds back CHOWN, SETUID and SETGID), both listed in `x-check-compose-allow`. The service always runs in stage and prod; in dev it exists but does not start by itself. Logical dumps are the method for now; physical backups with WAL archiving wait until a database outgrows nightly dumps.

## Options considered

- **A backup container per database.** More moving parts and no single place that shows the state of all backups.
- **Physical backups (pgBackRest, WAL-G) from the start.** Point-in-time recovery, but it changes the database server's configuration and is more than small projects need.
- **Database data in a folder of the clone (bind mount).** Visible on disk, but deleting the clone deletes the data.
- **Encrypt with one tool, copy with another.** Two tools to configure and check; restic encrypts everything it stores by itself.
- **The server rotates the copy (`forget --prune`, the first version).** Needs the right to delete on the storage: whoever breaks into the server can erase every copy as well as the local sets.
- **SFTP with some requests denied (`sftp-server -P remove,rmdir,…`).** Measured not to be write-only: restic needs rename and chmod, and with them the login can chmod an existing snapshot and overwrite it, or move `config` away so the copy cannot be opened. Every restic command also leaves a lock the server cannot remove, which blocks `check` and the storage side's `prune` until it runs `restic unlock`.
- **rest-server `--append-only --private-repos` (chosen as the example).** Every delete or overwrite of an existing file except a lock is refused; `check` works and leaves no lock; the storage side rotates the same folder.
- **rclone `serve restic --append-only` behind an SSH forced command, or object storage with keys that cannot delete or an object lock.** restic documents the first; neither was measured here.
- **One safety set per restore, kept for ever, or none.** Kept for ever, they fill the disk; with none, a restore of the wrong set loses the state it replaced. One per store keeps the cost fixed.
- **`CONFIRM=yes` alone to confirm a restore.** An exported `CONFIRM=yes` once replaced a database without anyone asking; typing the name needs a person.

## Consequences

Restores are tested continuously, not on the day of an incident, and a missing off-server copy shows up as an unhealthy container. Losing `BACKUP_COPY_PASSWORD` makes the copy unreadable, so it is kept in a safe place as well. The storage side needs its own rest-server (TLS in front on the internet) and a rotation job that has the repository password, so whoever rotates can also read the copy. A rotation that keeps every set of seven days also keeps a safety set of each of those days; keeping exactly one of them and resisting garbage sets pull against each other, and the owner chose the window. Garbage sets that a broken-into server adds (and the duplicates of `restic tag`) use the storage until the storage side removes them; sets dated in the future stay after the window passes, and with many of them only the last window is guaranteed. The PostgreSQL documentation itself says pg_dump is generally not the right choice for regular backups of production databases; this standard accepts that trade-off for small databases on purpose and leaves the move to physical backups for a later ADR.

## Verified

Checked on 2026-10-21, Docker 29.7.2, Compose v5.5.0, WSL2 Ubuntu 24.04; restic/restic:0.19.1@sha256:136600b6ff6843d61d355f7f71f460a166429f35de6fd11b568fece3c9a4d510, restic/rest-server:0.14.0@sha256:d2aff06f47eb38637dff580c3e6bce4af98f386c396a25d32eb6727ec96214a5, atmoz/sftp:alpine@sha256:7e439fabeae536fa254340724c042e11999924d906417dbb5c73602ad518813f. One-off runs, with restic called directly (not through the backup image):
- SFTP, users with `-P` lists. Without `rename` `restic init` fails. Without `remove`, `rmdir` and `posix-rename`, `init` and `backup` work, but every command leaves its lock (`Remove(<lock/…>) failed … permission denied`), `check` exits 11 while any lock is younger than 30 minutes, `unlock` cannot remove even a stale one, and the storage side's `prune` fails with the server's lock on the repository. With `setstat` also denied restic cannot lock at all. With the requests restic needs, `sftp -b` showed the login overwriting a snapshot after `chmod 600` and moving `config` away (afterwards `Fatal: repository does not exist`, exit 10).
- rest-server `--append-only --private-repos`, the server's login: `init`, 13 daily and 3 safety sets and `check` (also `--read-data-subset`) work and leave no lock. `forget <id>`, `forget --keep-last 1 --prune` and `prune` get `403 Forbidden` and remove nothing. Raw HTTP `DELETE` or `POST` of an existing snapshot, pack, index, key or `config` gets 403; `DELETE` of a lock gets 200. `init` of another path gets 401. `restic tag` leaves a duplicate snapshot (its rewrite is refused only after the new snapshot is saved), so no command that rewrites snapshots runs from the server.
- Storage-side rotation on the same folder, with a full-access instance or restic on the folder: the daily and weekly forget with `--keep-tag before-restore`, then `forget --tag before-restore --group-by host,tags --keep-last 1`, then `prune`, kept the daily and weekly sets and exactly the newest safety set. After the server's login added four empty sets dated after the real ones, the same commands as a dry run would have removed every real set; with `--keep-within 7d` added they removed nothing. A flipped byte in a pack made the server's `check` and `check --read-data-subset 100%` fail (exit 1).
- Docker Desktop: `docker run --rm alpine:3.20 df -Pk /` and `df -Pk` of a named volume showed 17% used and about 831 GB available on the virtual disk, while `df -Pk /mnt/c` showed 95% used and 50.8 GB available on the Windows drive under it; `df` of `DockerRootDir` from the WSL distro showed another disk, not the images' one.
- The Debian base (checked 2026-10-19, one-off run, with openssh-client and curl added): postgres:16@sha256:f1c3376c26f2609ab9f29f71f824103fe2fcd8ee0346485cb6122a4f93df6f94 (Debian 13 trixie, uid 999) has gosu, flock, sha256sum, stat, mkfifo and cmp, and lacks curl, wget and ssh, as the Dockerfile header says. The set, drill, rotation, restore from the copy, health, curl notification, the no-curl refusal, BACKUP_DIR 999:999 mode 700, and processes as uid 999 without capabilities all passed (500,000 rows, set 35 MB, restore 7.1 s, drill 2.0 s). The Alpine base is postgres:16-alpine@sha256:721873c34ceb9f8d8fc265984940dc982404c105f19ad51be9fdc5970a6080ea (Alpine 3.24.2, uid 70).
- The earlier SFTP copy (2026-10-19, one-off run, the template's first copy path, now dropped): end to end with an ed25519 key and `known_hosts` against atmoz/sftp (OpenSSH 10.3p1), with 2,000,000 rows (database 398 MB, set 137 MB): set 12.1 s, first copy 7.4 s, restore from the copy 10.0 s.
- `tests/backup/run.sh` (repeated by `make check`) proves what the template does with these findings: the copy on an append-only rest-server, the server's login refused on `forget` and `forget --prune` (403) with the snapshot count unchanged and `check` passing (the refusal of `prune` itself and of raw `DELETE`/`POST` is the one-off item above), `copy-check` failing against a full-access login, the read check failing on a flipped byte, the storage-side rotation keeping the real sets against garbage, the safety set (made before a restore, ignored by `latest` and the drill, restored by name, one only, copied, kept by rotation, skipped by `--no-safety`), the refused superuser and owner roles, the refused backup folders, the refusal for too little free space (also of a drill by hand, refused before it writes, `/drill` left empty and not counted as failed, and going on with `--risk`, step d2), `restore --check` and `--plan`, one store of two, the health rules, and the heartbeat (exactly one GET after a good daily run, none after a failure, a monitor that answers 404 only warns). `tests/project/run.sh` proves the `make` side: the confirmation (typed name in a terminal, `CONFIRM=yes` only on the command line, refused from `MAKEFLAGS`, `GNUMAKEFLAGS` and a parent make), `S`, `SET`, `FROM` and `NO_SAFETY` not taken from the environment, and the targets.

Not checked: many sets dated in the future added with the server's login (one, dated 2099, was tried); TLS with a real certificate in front of the rest-server and `--cacert` with a certificate of its own; the server's login against an unreachable rest-server (restic retries for minutes); reading a different part of the copy each day so that all of it is read once a week; rclone and object-storage copies; an SFTP user in read-only mode for the check; a store of another kind than Postgres; a real Healthchecks.io or Uptime Kuma instance and its alerts; a Linux server (Docker Desktop on WSL2 only); a Docker Desktop "clean up data" reset (the docs name containers and images, not volumes).
