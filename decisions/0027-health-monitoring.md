# D-0027. Health monitoring through a socket proxy that only reads

> English · [Українська](0027-health-monitoring.uk.md)

**Status:** accepted · **Date:** 2026-10-21 · **Rules:** OPS-04, ENV-01, ENV-03

## Context

Nobody learns that a service of a live server has failed, except the backup, which has its own outside signal (D-0010). Docker already marks every container with a healthcheck as healthy or unhealthy, but the mark lives on the server. Restart policies are described in terms of exits, not of health, so, as far as the documentation says, an unhealthy container is left as it is. A monitor needs one place to ask, or one signal to wait for, that covers every service of an environment and needs no list kept by hand.

Reading that mark means talking to the Docker socket, and the socket is root on the machine. A service that faces the internet (even behind a token) must not hold it.

## Decision

A `status` service in stage and prod, built from [`templates/project/docker/status/`](../templates/project/docker/status/) (Python standard library, non-root, `read_only`), builds one JSON envelope for its own compose project and offers it to a monitor:

- **What it reports.** For each container of the project (found by the label `com.docker.compose.project`, one-off runs excluded): `status` (`healthy`, `unhealthy`, `starting`, `none` for a running container with no healthcheck, `down` for any container that is not running whatever its last health was, `missing` for a service seen since `status` started and gone now, `unknown` when its health cannot be read), `failing` (consecutive failures, already 1 while the status is still `healthy`), and `ms` and `output` of the last check run since the container started (null right after a restart, because Docker keeps the old results). It also reports the free space of the disk of Docker's data (`/`) and of every folder the template mounts under `/disk` (the backup folder, read-only), each `healthy` or `unhealthy` against `DISK_WARN`, never below `DISK_RESERVE`. The envelope's `status` is `pass`, `warn` (nothing failed, a service is `starting`) or `fail` (any other state, a disk below its threshold, or Docker unreadable), and `ok` means not `fail`. A removed container is remembered from the start of `status`; its image tag is the tree hash of the deployed commit, so a deploy that changes anything recreates `status`, which then starts with no memory of the services the commit removed, and a removed service is not a false alarm.
- **How the monitor gets it.** `GET /status` with `Authorization: Bearer $STATUS_TOKEN` (at least 16 characters; `401` otherwise, checked before anything else, so also while failing) returns `200` for `pass` and `warn` and `503` for `fail`, with the same body. Every `STATUS_PUSH_INTERVAL` it also POSTs the envelope as `application/json`: `pass` and `warn` to `STATUS_PUSH_URL`, `fail` to `STATUS_PUSH_FAIL_URL`; an empty address sends nothing, so a monitor waiting for pings alerts on the silence; a failed push is only logged, without the address. `GET /health` without a token is the service's own healthcheck. `starting` is `warn`, not `fail`, because `make prod` recreates containers and each is `starting` until its `start_period` ends: a deploy must page nobody.
- **One monitor per environment**, not per service (below).
- **The proxy.** `status` reaches Docker only through `status-proxy`, [wollomatic/socket-proxy](https://github.com/wollomatic/socket-proxy) 1.13.1 pinned by digest (`sha256:3935b709275e4ec35d6ed5a5c4a1f0d01ed31eec5e7234efc3357ecd47689002`), a scratch image that runs as `65534:${DOCKER_GID}` (nobody, in the group that owns the socket on that server; `make bootstrap` writes `DOCKER_GID` into a new dev `.env` (on a server it is set by hand) and `make stage`, `make prod`, `make restart` and `make rollback`, the commands that start or recreate the proxy, refuse when it does not match the socket; backup, restore and `make images` never depend on monitoring), `read_only`, `cap_drop: ALL`, on an `internal` network shared only with `status`, with no published port. It allows `GET` of the container list and `GET` of `<project>-<service>-<n>/json` for this project's own names, built from `${COMPOSE_PROJECT_NAME}`, and refuses everything else: `403` for other paths and clients, `405` for other methods. The socket mount is `:ro`, but it is the allowlist that protects, not the flag. The template's stage and prod files list `docker-sock` in `x-check-compose-allow`, with the reason, and need no registry row.
- **The regex is grouped.** The proxy wraps each allowlist regex in `^…$`, so an alternative must sit in one group, `(?:a|b)`; ungrouped, `a|b` means "starts with a, or ends with b".
- **The healthchecks and the application's `/health`** follow the rules of OPS-04; tested lines for common images are in the [catalog](../catalog/README.md#healthchecks).
- **Later, not now:** the CPU and memory of containers (cAdvisor or the like).

## Options considered

- **Which proxy.** [tecnativa/docker-socket-proxy](https://github.com/Tecnativa/docker-socket-proxy) gives access by URL prefix: `CONTAINERS=1` allows every `GET` under `/containers`, which includes `logs`, `archive` (read any file of any container) and `export`. [linuxserver/socket-proxy](https://github.com/linuxserver/docker-socket-proxy) can deny logs, archive and export, but with `CONTAINERS=1` the inspect of every container on the host stays allowed. wollomatic's per-method regex allowlist is the only one of the three that expresses "the list, and inspect of this project's names, nothing else", and its image is `FROM scratch`, non-root, with a healthcheck of its own and a hostname-based client allowlist (`-allowfrom=status`).
- **How much Docker may show.** A: the list only; `ms` and `output` are `null`. Smallest exposure. B: the list and the inspect of this project's containers by name (chosen by the owner): the full envelope, at the price that a compromised `status` can read the environment and command of its own project's containers, which the inspect returns. C: the inspect of any container, which would turn a bug in an internet-facing service into the secrets of every container on the host, other environments included: rejected. A proxy filters requests, not replies, so it cannot strip `Config.Env` from an inspect.
- **Proxy as root.** It works with `cap_drop: ALL` (measured), but needs a `user` exception in `x-check-compose-allow`; `65534:${DOCKER_GID}` needs none beyond `docker-sock`.
- **Where the environment name comes from.** `${COMPOSE_PROJECT_NAME}` interpolated in the compose file always equals the name Compose really uses, also with `-p`, and needs no `.env` value. Looking the project up by the container's hostname works with a list-only proxy but breaks when a service sets `hostname:`.
- **A push to one address, or a pull only.** With one address, a monitor counts every ping as alive and decides failure by the address, so a POSTed envelope with `"ok": false` to a bare address is a success (Healthchecks.io decides by `/fail`, a keyword set by hand, or nothing; Uptime Kuma reads `status` and `msg` from the query and ignores the body). So there are two addresses, which also keeps the template free of any one product (each service fits by its own URL). A poll only is simpler and sees an unreachable site, but `/status` must then be on the internet, the monitor must send a header, and a private stage cannot be reached; so both are offered, and prod has an outside check of its public site as well.
- **`200` with `ok: false` for a failure** (the first version): any HTTP monitor reads that as up. All three conventions are compatible with `503` for a failure and `200` for degraded: the IETF draft asks `4xx-5xx` for `fail` and `2xx-3xx` for `warn`, Spring Boot maps `DOWN` to 503 (it has no degraded state), ASP.NET Core defaults `Unhealthy` to 503 and `Degraded` to 200. Both Uptime Kuma (accepted codes `200-299`) and UptimeRobot (down above 399) treat `503` as down with no setup.
- **`starting` as `fail`.** Every deploy would page the owner. Docker bounds the state: failures count after `start_period` and a container becomes `unhealthy` after `retries` of them, so a real failure is not hidden for long.
- **One monitor per service.** The alert names the service, but one incident gives several alerts (the database, then the application and the worker that depend on it), a new service needs a new monitor and a removed one leaves a monitor that goes down, and Healthchecks.io's free plan has 20 checks (3 projects × 2 environments × about 5 services would be over it). Per-service checks by auto-provisioning at Healthchecks.io (`?create=1` with a ping key) were not taken: tied to one product, stale checks, and the key lets anyone who holds it create checks. One monitor per environment is the template's choice, and the body names the failing service.
- **Silence as the only signal (no fail address).** Works for a dead server, but a service that fails is reported only after the monitor's period and grace.

## Consequences

An environment is watched by one monitor with no list kept by hand. The owner sets up the monitor (one check per environment, a period and grace that cover a deploy, the alerts) and runs one alarm drill by stopping `status` on stage; the template's tests cannot show that the outside monitor really alerts. Docker is read through one extra container of about 6 MiB, and `status` itself takes about 21 MiB. `STATUS_TOKEN` is a secret in `.env`. A removal of a container while `status` was down is not noticed. A project name that starts with another project's name followed by `-` (`shop-prod` and `shop-prod-old`) would match the regex of the shorter one; a `container_name:` outside `<project>-<service>-<n>` makes the inspect refused, and the health then comes from the list (Docker API 1.52 or later), without `ms` and `output`, or is `unknown` and a failure. The list is host-wide and carries each container's `Command`, so a secret in a command line is visible to anyone who can reach the proxy. The disk reading on Docker Desktop is indicative only.

## Verified

Checked on 2026-10-21, Docker 29.7.2 (API 1.55), Compose v5.5.0, WSL2 Ubuntu 24.04; python:3.12.13-slim@sha256:229a2c5bfa27522db7815ea81f9bed70af17ccb9de9fc7ad142b1877b5830d36, wollomatic/socket-proxy:1.13.1@sha256:3935b709275e4ec35d6ed5a5c4a1f0d01ed31eec5e7234efc3357ecd47689002.
- `tests/status/run.sh` (17 steps, repeated by `make check`) proves the service: the token (`401` with none or a wrong one, also while failing); all healthy gives `200` and `"status": "pass"`; one service unhealthy, stopped (`down`), removed (`missing`), a disk below `DISK_WARN` or `DISK_RESERVE`, and the proxy stopped (`error`) each give `503` and `"status": "fail"`, and healing gives `200` again; a service that is `starting` after a restart gives `200`, `"status": "warn"`, `"ok": true`; the raw output of the healthcheck is passed through; no planted secret of the environment or command line reaches the answer or the push; a container of a second compose project never appears; `ms` and `output` are null after a restart until a new check runs; a refused inspect falls back to the health in the list, and `unknown` is a failure; pushes: at least two POSTs of `application/json` with the full envelope to `STATUS_PUSH_URL` while healthy and none to `STATUS_PUSH_FAIL_URL`, the reverse while failing, nothing at all while failing with `STATUS_PUSH_FAIL_URL` empty (logged `status: now fail: no push, empty STATUS_PUSH_FAIL_URL`), a 404 or a refused connection only logged (`status: push failed: HTTPError: Not Found`), and for the refused connection the log does not hold the address; the proxy: `200` for the list and for this project's inspect by name, `403` for inspect by id, for another project's name (with and without `/v1.52`), for `logs`, `archive`, `json/../logs`, `/info`, and for a client not in `-allowfrom`, `405` for `POST` create, start, stop, exec and for `DELETE`; non-root (`status` does not run as root, the proxy runs as `65534:$DOCKER_GID`).
- One-off runs (2026-10-21): mutations of `status.py` for the codes, `warn`, the two push addresses, the silence, `unknown` and the null `ms` and `output`, one at a time, each turned the step that guards it red; the proxy answered `403` to `export` and `top` of a container; Docker keeps the last 5 results in `State.Health.Log`, oldest first, each cut to 4096 bytes plus `...`; a check that exceeds its timeout gives `ExitCode -1`; `FailingStreak` counts past `retries` and is already 1 while `Status` is `healthy`; after `docker restart` the status is `starting` with the old five results still in `Log`; a stopped container keeps its last health (`exited` and `unhealthy`); with `start_period` the checks run every `start_interval` (5 s by default), not every `interval`. The list `GET /containers/json` has no `Health` at `/v1.51/` and has it from `/v1.52/`; the inspect has `Config.Env` with the secrets passed as variables, and the list's `Command` showed `--requirepass …`. An ungrouped `a|b` regex let `/containers/json/../<id>/logs?stdout=1` through (Docker answered `301`); grouped, the same request got `403`. `Compose` interpolated `${COMPOSE_PROJECT_NAME}` as the file's `name:`, as the `-p` value, and as the variable's value. `statvfs("/")` in a `read_only` container reported the same filesystem as a named volume, and a read-only bind mount the filesystem of its host folder; on Docker Desktop both virtual disks reported 1006.85 G size and 792 G free while the Windows drive under them had 48.4 GB free. A wrong `DOCKER_GID` made the proxy exit with code 2 (`socket not available … permission denied`) and the deploy fail with `dependency failed to start`. Memory in use: `status` 20.7 MiB, the proxy 5.7 MiB. Healthcheck pitfalls: `pg_isready -U nobody` exits 0; `redis-cli ping` against `--requirepass` exits 0 and prints `NOAUTH Authentication required.`, so the container stays healthy; `mysqladmin ping` with a wrong user exits 0.

Not checked: the trivy findings of the `status` image; the disk reading on a real Linux server (overlay2, containerd snapshotter), and the `f_bavail` / `f_bfree` difference (the tests' tmpfs reserves no blocks); which monitors accept a JSON POST and what each does with the body (read from their docs and code, not run); Healthchecks.io channels other than e-mail showing the body; UptimeRobot free-plan custom headers and its terms of use (sources conflict); Better Stack and Cronitor body handling; Uptime Kuma's HTTP monitor with a JSON query on a `503`; that plain Docker never restarts an unhealthy container (the restart-policy page names exits only, and only forum posts say the rest); Docker engines older than API 1.52; a container removed while `status` was down.
