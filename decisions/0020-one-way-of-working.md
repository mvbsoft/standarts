# D-0020. Every project is worked the same way

> English · [Українська](0020-one-way-of-working.uk.md)

**Status:** accepted · **Date:** 2026-10-18 · **Rules:** PRN-10, ENV-05, DOC-04, QLT-01, QLT-02, QLT-03

## Context

Projects in different languages had different commands for the same job, separate targets to create and to update an environment, and checks that ran only when someone remembered them. Moving between projects meant learning each one again, for people and for agents alike.

## Decision

- **The same targets, the same behaviour.** The `Makefile` comes from `templates/project/Makefile`; a project changes only its settings block at the top (the own images, the application service, the commands, the external networks, the server branches) and its "Project targets" block at the end. A command of the project's own (an asset build, a worker, a report) is a target in that block, with a `## ` help text, so `make help` lists it, and a row in the README section; its name is not a standard target's. An update of the standard keeps both blocks.
- **One command per environment.** `make dev`, `make stage` and `make prod` create the environment the first time and update it every time after.
- **The README says it first.** Its first section, "Working with this project", lists every scenario with its command, what it does and what to do when it fails, plus the table of when each check runs; `AGENTS.md` links to it.
- **A pre-push hook runs the gates before a push.** `.githooks/pre-push` runs `make gates` in the working tree, which must hold the commit being pushed; `make bootstrap` installs it with `core.hooksPath .githooks`, because a clone does not bring hooks. The gates check the files as they are, so uncommitted changes count: in a terminal the hook lists them and asks "Nothing forgotten to commit? Continue? [y/N]", and only a yes (`y`) goes on; without a terminal (an IDE, an agent, a script) it prints the list as a warning and goes on. It does not try to tell an agent from a person: the agent's rule, in the template's `AGENTS.md`, is to ask the owner in the session before any `git push` while `git status` shows uncommitted changes. A push of a branch or a tag whose content differs from the checked-out commit is refused, and so is a push during whose gates `HEAD` moved or a file changed. The hook never uses `git stash`.
- **Two floors of check commands.** The base commands `lint`, `test`, `e2e`, `security` and `infra` each run the checks of one area, set by one line of the `Makefile` settings (`LINT`, `TEST`, `E2E`, `SECRETS` and `SECURITY`; `infra` has none), and none includes another. The group commands only run base commands, but for one step: `gates` runs `lint`, `test` and the `SECRETS` step of `security` (its summary line is `secrets`); `verify` is `lint`, `test`, `e2e`, `security` and `infra`. Both end with a summary of one line per base command. `fix`, `mutation`, `mutation-diff` and `image-scan` stand outside the groups and are started by hand. `LINT`, `TEST` and `SECRETS` are mandatory: empty fails, `off` is the owner's recorded choice (QLT-02).
- **Gates stay fast.** `make gates` aims for under five minutes; slower checks and those that need the network go to `verify` (before a task is merged), mutation testing to `mutation-diff` and `mutation` (before a large change is merged, started by hand: nothing runs them by itself, and the owner chooses whether the project has them), and the scan of the images of a commit to `image-scan` (before a change is merged to the prod branch; M wherever there is prod).
- **The gates are local.** They run in the git hook and can be bypassed (`--no-verify`, a merge in a web interface, an IDE that runs no hooks, a clone without `make bootstrap`). A CI is the owner's addition; it calls the same `make` commands.
- **Every check runs in the dev container, but the Dockerfile check.** `make lint` first checks the Dockerfile of every own image with `docker build --check` on the host ([D-0026](0026-quality-tools.md)). The code security scan (semgrep) is a tool of the dev image; the image scan (trivy) is one too. The dev container has no Docker of its own, so `make image-scan` builds the images of the checked-out commit on the host the way a server builds them ([D-0025](0025-images-built-on-the-server.md)), saves each with `docker save` to `build/image-scan/` in the project folder, which the dev container mounts, and trivy reads the files (`trivy image --input <file> --exit-code 1`); the files are removed afterwards. trivy reads the project's `trivy.yaml` and `.trivyignore`; the template's `trivy.yaml` fails on CRITICAL findings that have a fix, and the project tightens it. Mutation testing runs in a container of its own, the `mutation` service of the dev file, which uses the dev image, code and environment with the limits `MUTATION_CPUS` and `MUTATION_MEM` of `.env` and is removed afterwards (`docker compose run --rm`), so a long run cannot starve the dev container. Every mutation tool mutates all the code by default, so `MUTATION_DIFF` names its own base (QLT-01): Infection with `--git-diff-lines --git-diff-base`, cosmic-ray with `cr-filter-git`, StrykerJS, which has no git mode, with `--incremental` against its own previous report (the first run without one mutates all the code).

## Options considered

- **Each project its own commands.** Fits each stack, but nobody remembers them, and an agent guesses.
- **A project's own commands without targets**, run through `make shell` and written in `AGENTS.md`. Nothing new in the `Makefile`, but `make help` does not show them.
- **A separate `project.mk` that the `Makefile` includes.** The `Makefile` stays the same everywhere, at the cost of one more file.
- **Separate targets to create and to update** (`stage-up`, `stage-update`). Two commands for one intent, and the wrong one gets run.
- **Gates in a pre-commit hook.** Runs on every commit and gets skipped once it is slow; pre-push runs once per push.
- **Gates on the working tree as it is, with a question.** Chosen. The gates can be green for a red commit when an uncommitted fix hides it, and red for a good commit when an uncommitted break spoils it; that is why the hook lists the uncommitted files and asks in a terminal, warns where it cannot ask, and the agent is told to ask the owner.
- **Setting the uncommitted changes aside with `git stash` around the gates.** It checks exactly the commit, but the hook grew to about 110 lines with edge cases (worktrees of one repository taking turns, an interrupted push, a killed process, a gate that changes files while the changes are away). Replaced by listing and asking.
- **One setting per group (`GATES`, `VERIFY`, `SECURITY`).** The same check sat in more than one list and the groups overlapped; replaced by base commands that groups only run.
- **Gates only in CI.** Catches the problem after the code has left the machine, and needs a CI the project may not have.
- **Scans on the host** (a setting with host commands that may only call `docker run <pinned image>`). No saved files, at the cost of one more setting and commands outside the dev container.
- **trivy reads the image from a registry** (`--image-src remote`). No saved files, but it needs a registry, which the standard does not use ([D-0025](0025-images-built-on-the-server.md)).

## Consequences

Someone who knows one project knows them all. Once `make bootstrap` has installed the hook in a clone, a push from it cannot leave with red gates unless `--no-verify` is used, which is for an emergency only; the gates check the working tree, so a push with uncommitted changes is checked together with them, after the person confirmed in a terminal or the hook warned. A gate that grows slow has to move to `verify`, or it will be skipped. The image scan builds the images itself, so it can run before a change reaches the prod branch; it needs room for the saved files while it runs, and the images it built stay on the machine. The dev home is not writable, so the dev service sets `TRIVY_CACHE_DIR` to the project's `.cache/trivy` (in `.gitignore` and `.dockerignore`): without it trivy stops with `mkdir /.cache: permission denied` while it downloads its database. The tools, their versions and the reasons for them (which trivy releases are excluded, ESLint 10, `deptrac/deptrac`, the pip-audit and `uv audit` limits, the Semgrep rules licence) are in [D-0026](0026-quality-tools.md), so that a new release of a tool changes that record and not a rule.

## Verified

Checked on 2026-10-21 with `tests/project/run.sh` (sections b1 to b3): `make gates` is green on the sample and a red gate refuses `git push` for a branch and for a tag; a tag of another commit is refused; a push that only deletes a branch passes. In a terminal (the test gives it one through `script`) the hook lists a staged change, an unstaged one and an untracked file and asks; `n`, an empty answer and `yes` push nothing and run no gate; `y` runs the gates on the working tree as it is, pushes, and leaves the working tree and `.env` as they were, with an empty `git stash list`; with `y`, an uncommitted change that breaks a test refuses the push. Without a terminal there is no question and a warning names the files; a clean working tree gets neither. A push of another branch with other content is refused. A file written during the gates (in a tracked file, in a file that was already changed, and a new one) refuses the push and stays where it was written; a `HEAD` that moved refuses it; an untracked repository inside the project and a dirty submodule do not change the verdict of the gates; a push from a linked worktree checks that worktree's files and leaves the main one untouched. Measured earlier (one-off run, 2026-10-18): the hook runs even on a push that is "Everything up-to-date", and a non-zero exit refuses the push.

Checked on 2026-10-19, Docker 29.7.2, Compose v5.5.0, git 2.43.0 (WSL2), trivy 0.75.0 pinned by digest in the dev stage of the `tests/project` sample.
- `make image-scan` builds from the commit: `tests/project/run.sh` section c with an uncommitted change and an untracked file in the clone; the own images were built and saved to `build/image-scan/<image>.tar` (`app` and `backup` when this was measured, before the `status` image existed; the test now builds `app`, `backup` and `status`), the image held the committed file and neither the change nor the untracked file, `build/` was gone afterwards, and a second run built nothing.
- Its refusals: the same section; a commit with a git submodule is refused before anything is built, and a dev image without trivy gives `make image-scan needs trivy in the dev image (standard QLT-01)` after the build.
- The trivy database (one-off run, 2026-10-19): the first scan downloaded about 130 MiB in about 18 s into `.cache/trivy`; later scans of both files reused it. Before `TRIVY_CACHE_DIR` was set, trivy could not cache it, because the dev home `/` is not writable.
- The policy (one-off scan, 2026-10-19): stock `python:3.12.13-slim` with every severity; 328 findings, 56 of them HIGH or CRITICAL with a fix, so such a scan is always red, and the template's `trivy.yaml` starts with CRITICAL findings that have a fix. The numbers change with the base image and with trivy's database.
- The mutation container: `tests/project/run.sh` section b5, with `MUTATION_CPUS=1` and `MUTATION_MEM=256m` in `.env`; inside it `cpu.max` read `100000 100000` and `memory.max` `268435456` (cgroup v2; the test also accepts the cgroup v1 files), the container was gone afterwards, the dev container was not recreated, no second image was built, and `$(STAGE_BRANCH)` in `MUTATION_DIFF` reached the container as `main`. The command was `cat` of those files, no mutation tool, and starting and removing the container took about 4 s (one-off timing); that says nothing about the cost of mutation testing.
Not checked: whether the sample's images pass the template's `trivy.yaml` (the test accepts either result), a scan without network once the database is cached, images larger than the sample's (43 MB and 127 MB), and the mutation tools themselves: their `MUTATION_DIFF` forms come from their documentation (Sources).
