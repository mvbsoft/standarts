# D-0012. Logs go to stdout with one format in every environment

> English · [Українська](0012-logs.uk.md)

**Status:** accepted · **Date:** 2026-10-18 · **Rules:** OPS-03

## Context

Log files inside containers fill disks and disappear with the container; a format that differs between stage and prod means stage cannot check prod's log handling.

## Decision

Services write to stdout and stderr, Docker rotates the logs (`json-file`, 10m×3, in dev too), the format is the same everywhere, and only the level differs, through `LOG_LEVEL` (dev and stage may use `debug`, prod `info` or higher). Logs never contain secrets or tokens.

A replaced container takes its logs with it, so before `make stage`, `make prod`, `make rollback` or `make restart` replaces one, its logs (everything Docker still holds, up to 10m×3) are saved as `<UTC time>-<service>.log` in `LOG_ARCHIVE_DIR`. An empty variable means no archive; if the logs cannot be saved because the folder is not writable, nothing is replaced; too little space is an estimate, so the command warns and asks. Its files can be read by their owner only (and the folder the deploy creates). Nothing removes the old files: the folder grows until the owner clears it (cron, logrotate or by hand). The template's default is a folder in the clone; the owner chooses the folder when the standard is applied.

## Options considered

- **Files in a mounted log folder.** Needs its own rotation and mixes up environments.
- **No archive, the logs of the old container are lost.** What was written just before a failure is gone after the next deploy.
- **A log driver that ships logs elsewhere (a log service).** Keeps everything, but needs a service and an account the standard does not assume.
- **The script cleans the archive.** Deletes files the owner may still need; the owner asked to remove them by hand.

## Consequences

The log handling verified on stage is the log handling of prod. After a deploy the logs of the old version are in the archive folder, at the price of about 18 MB and 0.8 s of copying for a container at its limit (one-off measurement, 2026-10-21); the script reserves the largest the `json-file` limit allows, 30 MB (10m × 3) per container, plus `DISK_RESERVE`. The archive folder grows without bound until the owner clears it.

## Verified

Checked on 2026-10-21, Docker 29.7.2, Compose v5.5.0 (WSL2):
- (one-off run) A service with `json-file`, `max-size` 10m and `max-file` 3, recreated with a changed environment: the old container was gone (`docker inspect` failed) and `docker compose logs` showed only the new container's lines.
- (one-off run) `docker logs --timestamps` of a container at the 10m×3 limit, after it wrote 25 MB to stdout, took 798, 831 and 805 ms over three runs, printed 13,528,198 bytes without the timestamps, and the file it made with `--timestamps` was about 18 MB (the number the consequences use).
- `tests/project/run.sh` (repeated by `make check`): after a deploy the newest `*-app.log` holds the old version's lines and none of the new one's; nothing is archived when nothing is replaced; `make restart` archives only the replaced container; an empty `LOG_ARCHIVE_DIR` archives nothing; a read-only folder refuses the command with the container unchanged; a folder on a disk without room refuses it without a terminal and without `RISK=yes`, and goes on with the warning with it; the dev compose carries the same `json-file` limit.
