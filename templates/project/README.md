## Working with this project

Every project built by the standard works the same way. You need Docker with Compose, `git`
and `make` (the exact list and versions: standard PRN-01); everything else runs in containers. `make help` lists all commands, in groups.

| Situation | Command | What it does | If something goes wrong |
|---|---|---|---|
| First time on this machine | `make dev` | creates `.env` from `.env.example` (a `.env` the project already has, such as Laravel's, stays: it names the variables of `.env.example` that `.env` lacks, for you to add), installs the git hooks, builds the images, starts the stack, runs the migrations, prints the addresses. The application itself starts with `make run` | a missing tool or a port in use is named in the error; fix it and run `make dev` again. Another clone of this project already runs here: "A second copy for parallel work" below |
| Daily development | `make dev`, then `make run`; `make shell` for the tools | `make dev` starts or updates the stack; `make run` runs the application in the dev container (the `RUN` setting of the `Makefile`) until Ctrl-C; `make shell` opens a shell there. Code changes are live, nothing to rebuild | `this project has no RUN command (set RUN in the Makefile settings)`: this project has not set `RUN` yet. `make logs` follows every service (`S=<service>`: one; `TAIL=<n>`: the last n lines, then it ends); `make down` stops the stack and keeps the data |
| Dependencies or a Dockerfile changed | `make dev` | rebuilds only what changed, then starts | a build error names the step that failed |
| Test data | `make seed` | fills the dev database with test data | — |
| A second copy for parallel work | a git worktree: `make dev` in that folder; another clone: `make dev NAME=2` on its first `make dev` | the copy gets its own containers, database and free ports and prints its addresses (`NAME` counts only on the command line, and only while the clone has no `.env`) | a plain second clone is refused while the containers of the first one exist, stopped ones too, since the two would share them and the database; a clone that already has a `.env` (a copied folder) sets `DEV_SUFFIX=-2` and `APP_PORT=` in it. The messages and what to do: [operations](docs/how-to/operations.md), "One copy of each environment per machine" |
| Before every push | nothing: `git push` runs `make gates` | `make lint`, `make test` and the secret scan, in this working tree, then the summary (one line per check: `ok`, `FAIL`, `off` or `skip`, and the last line of its output, of the step that failed first). The gates check the files as they are: with uncommitted files, `git push` in a terminal lists them and asks `Continue? [y/N]` (`y` runs the gates and pushes; anything else pushes nothing); without a terminal (an IDE, an agent) it lists them in a `WARNING` and goes on. Every branch and tag pushed must have the content of the checked-out commit, so push one branch at a time from its checkout (`git push --all` or `--tags` is refused when they differ); a push that only deletes runs no checks | the push is refused and the summary names the failing check; fix it and push again. `pre-push: the gates changed files …`: a gate must only check (or you edited files during the push: push again). `pre-push: HEAD moved during the push`: a checkout or a commit ran meanwhile; push again |
| Simple findings of the checks (format, import order) | `make fix`, then `git diff` and `make gates` | the fixers of the lint tools (`FIX` in the `Makefile` settings), in their safe mode; only by hand, never by the gates or a hook | the remaining findings are fixed by hand |
| One kind of check | `make lint`, `make test`, `make e2e`, `make security`, `make infra` | each runs one kind alone: `lint` the code not run (first `docker build --check` of the Dockerfile of every own image, on the host; then format, lint, types); `test` the code run, fast and offline; `e2e` the whole application (API contract, browser); `security` the secret scan, then SAST and the dependency audit (network); `infra` `check-compose`, `parity`, then `make backup-test`. `LINT`, `TEST` and `SECRETS` are mandatory: empty refuses (and fails `make gates`); `off` says this project does not want that check. The settings are at the top of the `Makefile` | the output names the failure |
| A task is finished | `make verify` | all five of them, each also after another failed, then the summary | the summary names each failing check |
| Ship a change to stage | `make stage` (on the stage server), after the task is merged into `<STAGE_BRANCH>` | takes the stage branch and builds the images of that commit the server does not have yet (from the commit itself: nothing uncommitted on the server reaches them), runs the migrations, replaces what changed, prints `OK: stage runs <commit>`, then checks the tuning. It refuses a second copy of stage on this machine, warns and asks about a disk without room (`RISK=yes` on the command line answers without a terminal), and saves the logs of the containers it replaces. Every step: [operations](docs/how-to/operations.md), "Update" | every step stops on failure and what already runs keeps running; after a failed start, `make rollback`; after a failed tuning check the deploy is recorded: fix the value in `.env` and `make restart`. The messages and what to do: [operations](docs/how-to/operations.md), "When something fails" |
| Before a change goes to prod | `make image-scan` (on `<STAGE_BRANCH>` up to date with origin) | builds the images of the checked-out commit the way a server does and scans them with trivy in the dev container, by the project's `trivy.yaml` and `.trivyignore`; prints `image-scan: OK`. The first scan downloads trivy's database (about 130 MiB) into `.cache/trivy`. The scanned images stay on this machine (`docker images '<repo>-*'` lists them, `docker rmi <repo>-<image>:<tree>` removes one) | `image-scan: trivy failed or found vulnerabilities (above) in: <images>`: update what it names (the base image, a dependency) and ship again, or accept the finding in `.trivyignore` with its reason. `make image-scan needs trivy in the dev image (standard QLT-01)`: add trivy to the `dev` stage |
| Deploy to prod | get the change into `<PROD_BRANCH>` the way this project does it (for example a pull request from `<STAGE_BRANCH>`), then `make prod` (on the prod server) | deploys `<PROD_BRANCH>` like `make stage`: the prod server builds the images of that commit itself, from the content stage ran | as for `make stage` |
| A value in a server's `.env` changed (a secret, a limit) | `make restart` (on the server) | applies the changed `.env` to the commit that runs now: saves the logs of the containers it affects, recreates only those, no branch move, no migrations; checks the tuning; prints `OK: <env> runs <commit> (restarted with the current .env)` | `a container did not become healthy with the changed .env`: set the previous values back in `.env` and `make restart` |
| Go back to the previous version | `make rollback` (on the server) | deploys the previously deployed commit, without migrations; its images are normally still on the server, otherwise it builds them again | `make rollback did not finish (above): this clone is left at <sha> (detached HEAD); …`: the rest of the line says what `make <env>` and another `make rollback` would deploy |
| What runs now | `make status` | the checked-out and the last deployed commit, and the health of every service of this clone | — |
| Be told when something is wrong | nothing: the `status` service (stage and prod) watches every service and the free disk space for the monitor you set up. `curl -H "Authorization: Bearer <STATUS_TOKEN>" https://<host>/status` asks it by hand | every `STATUS_PUSH_INTERVAL` it POSTs its JSON to `STATUS_PUSH_URL` while everything is fine and to `STATUS_PUSH_FAIL_URL` on a failure; `GET /status` answers 200 (`pass`, `warn`) or 503 (`fail`) with the same JSON, which names the service or disk | the monitor alerts; the JSON says which service or disk. Set-up, alarm drill, messages: [operations](docs/how-to/operations.md), "Monitoring" |
| Back up now; check a restore | `make backup`, `make backup-drill` (`S=<service>`: one store; `SET=<set>`: drill that set) | a set of every store (copied off the server when `BACKUP_COPY_TO` is set); a restore of the newest sets into a temporary database, compared with them. The `backup` service does both by itself on a schedule (in dev only by command) | the error names the store and the reason: [backups](docs/how-to/backups.md) |
| Which backup sets there are; the state of the backups | `make backup-list` (`FROM=copy`: the off-server copy, on a server), `make backup-status` | the sets with their time, size and kind, the names `SET=` takes; the backup service's health and why, the newest sets and copy, the last result of every job | `make backup-status` names the reason: [backups](docs/how-to/backups.md), "When something fails" |
| Restore data | `make restore` (`SET=<set>`: that set, `SET=before-restore`: the state before the last restore; `FROM=copy`: from the off-server copy, on a server; `S=<service>`: one store; `NO_SAFETY=1`: no safety set) | first checks the set of every store (by default the newest set all stores have) and shows what it would replace (in red in a terminal); in a terminal you then type the database name, without one (an agent, a script, input not a terminal) only `CONFIRM=yes` on the command line of `make restore` confirms it; on a server then stops the application; makes a safety set of every store, replaces the working database with the set and compares it with the set. `S`, `SET`, `FROM`, `NO_SAFETY` and `CONFIRM` count only on the command line (CONFIRM never from `MAKEFLAGS` or a parent make) | the application stays stopped: `restore: the application is stopped: make restart starts it again` (on a server not deployed yet: `make <env>`). [backups](docs/how-to/backups.md) |
| The off-server backup copy is set up or changed | `make backup-copy-check` (on the server) | writes a small test set, reads it back and checks that this server cannot delete it (the set stays in the copy, tagged `copy-check`), then the read check of the copy (`BACKUP_COPY_READ` of its data): `OK` or the reason | the reason says what to fix: [backups](docs/how-to/backups.md) |
| <a command of this project's own, from the Makefile block "Project targets"> | `make <target>` | <what it does> | <what to do when it fails> |

### When each check runs

| When | What | Who starts it |
|---|---|---|
| after every edit by the agent | format, lint and, where possible, types of that file | the agent's hook, by itself |
| before every `git push` | `make gates` (`lint`, `test`, the secret scan, then the summary) | the git hook, by itself |
| when a task is finished, before it is merged | `make verify` (`lint`, `test`, `e2e`, `security`, `infra`, then the summary) | you or the agent |
| before a change is merged into `<PROD_BRANCH>` | `make image-scan` | you or the agent |
| daily, and weekly a restore drill | the `backup` service's set, copy and drill, then the heartbeat to the monitor (`BACKUP_HEARTBEAT_URL`) | the `backup` service, by itself |
| every `STATUS_PUSH_INTERVAL` (a minute by default) | the health of every service and the free space of Docker's disk and of the backup folder, to the monitor (`STATUS_PUSH_URL`, `STATUS_PUSH_FAIL_URL`) | the `status` service, by itself |
| when the gates fail on formatting or simple lint findings | `make fix`, then `git diff` and `make gates`; the agent runs it before it edits such things by hand | you or the agent |
| before a large change is merged | `make mutation-diff` (the changed code), or `make mutation` (all code) when you want a full picture | you or the agent |

Mutation testing (`make mutation`, `make mutation-diff`, the last row above) is the owner's choice
(standard QLT-01). When the owner says no, the agent removes it, the row above included, as the
standard's `templates/README.md` lists under "Mutation testing declined".
